# Проведённые эксперименты и оставшиеся задачи

Составлено 25.10.2026 по сообщениям и логам в чате, текущему коду и файлам results/.
Новые эксперименты при составлении этого файла не запускались.
«Нет данных» означает, что результат не записан, а не равен нулю.
Все приведённые оценки качества относятся к validation, не к test.

## Общие настройки

- Датасет HIGGS: 28 входных признаков и одна бинарная метка Y.
- Разбиение: train 70%, validation 15%, test 15%; stratify по меткам.
- random_state=12 в обоих разбиениях.
- StandardScaler: fit только на train, transform остальных выборок.
- Baseline: LogisticRegression(max_iter=1000), остальные параметры по умолчанию.
- Сеть: Linear(28,32) → ReLU → Linear(32,16) → ReLU → Linear(16,1).
- torch.manual_seed(12), Adam, lr=0.001, без dropout и weight_decay.
- BCEWithLogitsLoss; одно обновление на всём train за эпоху (full-batch).
- Класс сети определяется порогом 0.5 после sigmoid.
- Лучшие веса выбираются по минимальной validation BCE, не по accuracy.
- Первые запуски на 300 строках — CPU; полные запуски в присланных логах — MPS.
- Точное время запусков и версии окружения для исторических результатов не записаны.

## 1. Эксперименты на первых 300 строках

Train: 210 событий; validation: 45; test: 45.
Train содержит 90 событий класса 0 и 120 класса 1.
Validation и test содержат по 19 событий класса 0 и 26 класса 1.

| Вариант | Эпохи | Validation BCE | Validation accuracy | Правильных ответов |
|---|---:|---:|---:|---:|
| Всегда предсказывать класс 1 (мажоритарный baseline) | — | Не измеряли | 57.7778% | 26/45 |
| Логистическая регрессия | Не применяется: max_iter=1000 — лимит оптимизатора | Не измеряли | 71.1111% | 32/45 |
| Нейросеть, последние веса | 100 | 0.7288236021995544 | Не измеряли | Нет данных |
| Та же нейросеть, восстановленные лучшие веса | 48-я из 100 | 0.6849712133407593 | 53.3333% | 24/45 |

История того же 100-эпохового запуска:

| Момент | Train BCE | Validation BCE |
|---|---:|---:|
| Первая эпоха | ≈0.6897 | ≈0.7023 |
| Минимум validation, эпоха 48 | Нет записанного значения | 0.6849712133407593 |
| Последняя эпоха, 100 | ≈0.4044 | 0.7288236021995544 |

**Наблюдение:** train loss продолжает снижаться, validation после минимума
растёт. Это характерный признак переобучения на маленькой выборке.
Checkpoint позволил вернуть меньшую validation loss, но восстановленная сеть
по accuracy уступила логистической регрессии и постоянному классу 1.

Это один запуск с сохранением промежуточного состояния, а не два независимых
обучения на 48 и 100 эпохах. Разница loss и accuracy не является противоречием:
loss оценивает вероятности, accuracy — решения после порога.
На 45 событиях один ответ меняет accuracy на 100/45 ≈ 2.22 процентного пункта.

## 5. Что требует задание

Источник: UGP, лекция 17, Project 1 — Diagnosing neural network training.

- Многослойный классификатор, train/validation/test и простой baseline.
- Намеренно получить минимум две проблемы обучения и проверить способы исправления.
- Сравнить минимум три конфигурации при изменении одного фактора.
- Подходящие метрики, графики train/validation loss, причины проблем и обоснование выбора.

Эпохи являются возможным исследуемым фактором, а перечень в задании не закрытый.
Но для однозначного покрытия условия предлагается отдельное сравнение learning rate,
который прямо упомянут в задании. Финальная test-оценка выполняется после выбора.

## 6. План оставшейся работы — в текущем main.py

Без новой структуры папок, CLI, классов и тестовой инфраструктуры.

### Шаг 1. Сохранять результаты запуска

- Сохранить лучшие веса на диск, а не только в best_weights в памяти.
- Сохранить массивы train_losses и validation_losses, график и итоговые метрики.
- Записать число строк, seed, epochs, lr, архитектуру и лучшую эпоху.
- Использовать разные имена для разных опытов, чтобы не затирать результаты.
- Достать итог текущего 3000-эпохового запуска, если он ещё доступен в консоли.
  Если нет, так и оставить этот результат неполным, не выдумывать его.

### Шаг 2. Дополнить метрики baseline и нейросети

- Оставить accuracy.
- Добавить precision, recall, F1 и confusion matrix на validation.
- Посчитать validation BCE для baseline, чтобы сравнить вероятностные предсказания.
- ROC-AUC можно добавить как дополнительную оценку ранжирования.

### Шаг 3. Сравнить три learning rate

- lr=0.0001, 0.001, 0.01; Adam остаётся тем же.
- Для первого сравнения зафиксировать бюджет 300 эпох для всех трёх.
- Для каждого запуска заново создать модель с torch.manual_seed(12) и новый optimizer.
- Не менять одновременно слои, данные, разбиение, регуляризацию или full-batch режим.
- Сохранять графики, лучшую validation BCE, accuracy/F1 и время каждого запуска.
- Формулировать вывод именно для данного бюджета, а не «этот lr всегда лучший».

### Шаг 4. Закрыть требование двух проблем обучения и исправлений

Проблема A: переобучение на первых 300 строках уже наблюдалось.
Сравнение последней и лучшей эпохи показывает пользу выбора checkpoint по BCE.
Если нужно воспроизводимое подтверждение исправления, повторить этот маленький
опыт с сохранением графика и добавить early stopping либо один вид регуляризации.

Проблема B: недостаточный бюджет обучения на полном наборе.
Сравнение 100 и 300 эпох уже показало улучшение; длительный лог подтверждает
дальнейшее снижение BCE. Это проблема недостаточного обучения, а не доказательство
недостаточной мощности архитектуры. Сохранить и объяснить соответствующие кривые.

Если нужен более явный второй диагностический сценарий, отдельно попытаться
получить нестабильное обучение завышенным lr, затем уменьшить его при тех же условиях.
Само значение lr=0.1 или 1 не гарантирует нестабильности: проблема должна быть
показана результатами. Третий тип проблемы не обязателен, если две уже обоснованы.

### Шаг 5. Выбрать конфигурацию и провести финальную проверку

- Выбрать параметры и checkpoint только по validation.
- По возможности повторить лучшие варианты с несколькими seed, чтобы оценить устойчивость;
  это усиление анализа, а не явно указанное требование текста задания.
- Зафиксировать модель и порог, затем один раз оценить её на test.
- Оценить baseline на том же test для итогового сравнения.
- По test-результату не подбирать новую конфигурацию.
